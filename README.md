# 多平台电商存量经营分析项目

## 一、项目简介

本项目面向同时运营 **淘宝、京东、抖音** 三个渠道的电商业务，围绕「无法定位各平台转化流失卡点、缺少标准化用户价值划分、无法识别滞销/爆品 SKU」三大痛点，完成从**数据质量校验 → 多表关联 → 指标计算 → Cohort/RFM 生命周期分析 → EDA 特征洞察 → BI 看板 → 可落地运营策略**的端到端存量经营分析。

项目严格以 SQL（CTE + 窗口函数）为核心指标计算引擎，pandas 为探索分析与交叉校验工具，Excel 为第三方人工复算工具，并将全流程封装为可一键复跑的 Notebook / 命令行流水线。

**技术边界**：不使用 PCA 降维、K-Means 聚类等无监督算法，不做 A/B 实验；仅使用一次默认参数逻辑回归做下单转化的特征方向验证（训练集 AUC = 0.78；另附 5 组基线对照，「仅意图两特征」AUC 0.7702、「仅人口属性」0.5124、去掉意图后 0.6492，因此该模型只取系数方向与漏斗、EDA 结论交叉印证，不用于预测上线）；扩展专题（报告附录 C/D/G）对相关字段使用卡方 + Cramer's V / Spearman 观察性独立性检验，无实验分组、不做因果解读。

## 二、业务背景

- 业务模式：三平台货架/内容电商，经营 8 大一级品类 3,298 个 SKU，注册用户 5,486 人。
- 数据窗口：2025-01-01 ~ 2026-12-28（快照日 2026-12-31）。
- 核心诉求：① 定位分平台漏斗流失环节；② 建立 RFM 用户价值分层与 Cohort 留存体系；③ 识别爆品与滞销 SKU；④ 产出跨平台运营、用户维护、库存优化策略。
- 统一口径：有效订单 = `order_status='已完成'`；GMV = 有效订单实付总额。

## 七、亮点设计

1. **SQL ↔ pandas ↔ Excel 三重交叉校验，9 项核心指标三方一致**。SQL 腿以 `code/data_process.sql` 的 22 个 SECTION 为口径源头；pandas 不读 SQL 结果独立重算（`output/metrics/cross_check_sql_python.csv`，9/9 一致）；Excel 腿按旧版兼容写法（SUMIFS / COUNTIFS / VLOOKUP / SUMPRODUCT + 辅助列）在同一工作簿内重建，计算值缓存在 `cross_check.xlsx`，公式与逐步操作说明见 `excel_cross_check.md`。三腿分属三个独立计算引擎，防止「同一工具里同样的错误写法自我验证」。

2. **数据质量异常台账坚持「先统计、给两种方案、写明选择理由，不盲目删数」**。10 类异常逐条计数留痕：50.01% 订单下单早于注册、1.10% 用户×商品时序颠倒、0 条主键/外键/金额勾稽异常（27,523 行明细 0 误差），每条都记录「标记保留 or 过滤」的选择依据与对下游指标的影响范围。

3. **609 行 SQL 以 CTE 组织，11 个 SECTION 使用窗口函数**：漏斗相邻/累计环节转化用 `LAG()`/`FIRST_VALUE()`；RFM 打分与帕累托、爆品分桶用 `NTILE(4)`/`NTILE(5)`；会话内「用户×商品」最早记录的时序排查用 `ROW_NUMBER()`；用户与 SKU 的累计贡献曲线用 `CUME_DIST()`；等级/分层的占比用 `SUM() OVER ()`。复杂口径（RFM 打分方向、Cohort 窗口完整性标记、NTILE 与 CUME_DIST 头部切分口径差 1 人的原因）直接写在 SQL 注释里。

4. **31 个指标完整字典**（`report/指标字典.md`）：每个指标含业务定义、计算公式、统计过滤条件、口径说明四要素，特别区分了「有效购买转化率（分母=注册用户）」与「漏斗浏览→下单转化率（分母=浏览用户）」等易混口径；第 22~26 号为扩展专题指标（全量订单口径），第 27~31 号为口径衔接、时段/星期、维度同质性、复购间隔、累计贡献曲线指标，与 GMV 主口径分节管理。

5. **分析结论按置信度三档分级**：漏斗/GMV/RFM/帕累托/商品分层为高置信（三重校验一致），Cohort 留存绝对值与逻辑回归系数为中置信（受时序异常影响，仅取方向），设备影响/库存深度/地域细分/子品类明确「不做结论」；附录另附 Cohort 宽松口径、严格路径漏斗两组敏感性对照，以及扩展专题（订单状态/促销/篮子）的字段独立性证据，防止把噪声当业务结论。

6. **数据坑防护均在代码中留下**：`shipping_method` 字典 local/same_city 同名「同城配送」，直接 JOIN 会令订单金额翻倍，SQL 与 Excel 两侧分别以 `GROUP BY name + MIN(code)` 和 VLOOKUP 首命中规避；`"order"` 为 SQL 保留字须双引号；50.01% 订单早于注册日期在 Cohort 中以负 offset 剔除、在 GMV/RFM 中不受影响，分指标区别对待。

## 九、项目局限性

1. **公开数据集**，非线上生产数据，不存在真实大促与流量波动（月度 GMV 仅在 18~28 万元窄幅波动），结论不代表真实平台经营水平。
2. **营销字段无业务信号**：仅 5 类粗粒度 promotion 标记，无活动预算、曝光、触达数据；且用券/无券完成率 20.14% vs 20.16%（卡方 p=0.997）、成交/标价比率 0.002~70.97 无勾稽（详见附录 D），无法量化营销转化增益与 ROI。
3. **地域粒度仅到 city（10 城）**，无法做区县级分析；经纬度字段全为 0。
4. **无消息触达/召回记录**，召回策略是数据推论，无法验证实际召回效果。
5. **RFM 阈值基于该数据集**，且 50.01% 订单早于注册日期（Cohort 主口径不计入注册前订单，留存绝对值可能低估；附录宽松口径 30/60/90 天为 15.29%/16.49%/17.70%，结论方向不变），上线前须按真实复购周期重校准。
6. 库存字段只有「有货」无库存量、设备类型全为 mobile、子品类全为「其他」、tags/app_version 全空，库存深度、设备对比、子品类下钻均不具备数据条件。
7. **交易后段字段与商品组合为独立生成标记**：5 种订单状态各约 20% 且与平台/金额/促销/用券均无关联（卡方 p≥0.145），待付款+取消 40.02% 不能当真实流失率；每单固定 2~3 件跨品类商品，28 个品类对 lift 全在 0.67~0.76，无连带结构（附录 C/E）。
8. **多数维度经检验为均匀随机**：品牌（10 个）、支付方式（5 类）、配送方式（3 类）、性别、停留时长分箱与订单状态/金额带/平台/是否完成的 24 项卡方检验中 18 项 Cramer's V<0.05（附录 G）；下单时段与星期结构也仅反映自然日比例（工作日 72.65% 订单 vs 71.39% 自然日）。这些维度不产出运营结论——是「做了筛查并证明无可用信息」，而非「没做」。
