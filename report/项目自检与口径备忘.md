# 电商存量经营分析项目 · 指标口径自检与备忘（15 题）

> 覆盖范围：SQL 多表关联与窗口函数实现、数据质量校验、漏斗/RFM/Cohort 口径边界、业务结论解读、SQL↔pandas↔Excel 三方校验、PowerBI 设计、项目局限性与自我限定。
> 用法：作为**口径自查清单**逐条对照 `code/data_process.sql` 与 `output/` 落盘结果，用于确保对外解释与代码一致；本文件不是讲稿。
> 所有数字均来自本项目对 9 张业务表的真实计算结果（窗口 2025-01-01 ~ 2026-12-28）。

---

**Q1：先整体介绍一下这个项目，它和广告人群挖掘类项目有什么区别？**

参考答案：这是一个三平台（淘宝、京东、抖音）电商的**存量经营分析**项目，数据量是 5,486 用户、3,298 个 SKU、10,996 笔订单、21,998 条行为日志。业务痛点有三个：定位平台转化卡点、建立用户价值分层、识别爆品和滞销 SKU。我完成了数据质量校验、SQL 多表关联、转化漏斗、Cohort 留存、RFM 分层、帕累托、商品分层、EDA、BI 看板和运营策略六个阶段。和广告类项目的技术区分是明确的：**不使用 PCA、K-Means 等无监督聚类去「从流量里找人」，也不做 A/B 实验**（扩展专题里对订单状态/促销等字段做过卡方与 Spearman 独立性检验，那只是观察性描述统计、用于识别字段是否随机生成，不是实验分组结论）；唯一的机器学习是一次默认参数逻辑回归，用来做下单转化的**特征方向验证**——训练集（2,711 名浏览用户）样本内 AUC = 0.78，并附 5 组基线对照（仅人口属性 0.5124 / 仅平台 0.5429 / 仅意图两特征 0.7702 / 全集 0.7766 / 去掉意图 0.6492），说明判别力几乎全部来自「收藏 + 加购」这类中段意图特征；只取系数方向做业务解读（收藏 OR 3.91、加购 OR 2.31），与漏斗、EDA 结论交叉印证，不做调参、无交叉验证、不用于预测上线。核心工具是 SQL 窗口函数和业务指标体系。

**Q2：多表关联时你用什么 JOIN？字典表是怎么接进来的？踩过什么坑？**

参考答案：一律用 **LEFT JOIN 从事实表向字典/维度表关联**，保证事实行不因字典缺失而丢失，再统计未命中行数来验证关联质量。具体有四种关联键：订单的 platform 是编码，按 `platform.code` 关联；而 order_status、payment_method、shipping_method 在订单表里存的是**中文名**（如「已完成」），要按字典表的 name 列关联，按 code 关联会全部为 NULL。踩过的坑是 `shipping_method` 字典里 local 和 same_city 两个 code 都叫「同城配送」，直接 JOIN 会让同城订单翻倍、GMV 虚高；我在 SQL 里先用 `GROUP BY name + MIN(code)` 去重成一个 CTE 再 JOIN。另外 "order" 是 SQL 保留字，SQLite 里要写成 `"order"`。

**Q3：你的数据质量校验做了哪些事？结果如何？**

参考答案：四个维度。① **缺失值**：逐字段统计缺失数和占比；② **主键重复**：9 张表主键重复 0 条，5 张主表完全重复行 0 条；③ **外键完整性**：behavior→user、behavior→product、order→user、order_item→order、order_item→product 五条关系的孤儿记录全部为 0；④ **业务逻辑异常**：金额负数、支付早于下单、数量 ≤0、明细金额不等均为 0；但检出了时序异常——5,499 笔订单（50.01%）下单时间早于注册日期、12 对用户×商品（1.10%）下单早于浏览、2 个多用户共用会话。⑤ **字典合法性**：平台、状态、支付、配送编码非法数均为 0，但发现 platform 字典里有 pinduoduo、tiktok_shop 两个无业务数据的编码。每类异常都按「类型-数量-占比-处理选择-理由」写进了报告。

**Q4：发现缺失值你是怎么处理的？为什么没有统一填充或删除？**

参考答案：先区分「错误缺失」和「业务性缺失」，不能一个 dropna 解决。本数据里：`coupon_code` 缺失 50.20%（5,520 行），业务含义就是「该单没用券」，是正常业务形态，归类为「无优惠券」即可；`referrer` 缺失 32.54%，对应直接访问/无来源，标记为「未知来源」单列，不臆造渠道；而 `product.tags`、`user_behavior.app_version` 是 100% 全空，整列没有信息量，直接排除出分析集，也不填充。其余所有字段缺失为 0。删除会破坏平台、订单状态的结构分布，均值/众数填充会制造不存在的业务信息，所以只有在建模且算法要求时才考虑填充，本项目的指标计算完全不需要。

**Q5：50.01% 的订单下单时间早于注册日期，这个数你怎么解释、怎么处理？**

参考答案：这是注册日期和订单日期独立随机生成导致的逻辑冲突，我做了两层处理：第一，**标记保留不删除**——删掉一半订单会让平台和等级分布失真，且用户、金额本身没有错；第二，在不同指标里区别对待：GMV、RFM 不依赖注册日期，完全不受影响；Cohort 留存依赖注册日期，我把「下单日 - 注册日」为负的订单一律不计入任何留存窗口，并在报告里把留存绝对值标为中置信、提示可能低估。另外还有 12 对「同一用户同一商品下单早于浏览」（占双行为对的 1.10%，涉及 27 条日志），因为漏斗是按环节独立去重用户算的、不依赖同用户同商品的先后顺序，所以同样标记保留、不影响指标。脏数据处理的原则是：先计数、给两种方案、写清选择理由，绝不盲目 drop。

**Q6：转化漏斗怎么算的？为什么不用「同一会话路径」口径？**

参考答案：漏斗取 `user_behavior` 表，每个环节对 global_user_id 去重：全网浏览 2,711 → 加购 2,368 → 下单 1,953 → 支付 1,734，相邻环节转化率 87.35% / 82.47% / 88.79%，浏览→支付 63.96%。没有用严格会话路径，原因有两个：① 数据里 99.99% 的会话只有 1 条行为，根本无法串路径；② 各环节用户集合非严格包含（628 人有加购无浏览记录），日志是独立采样的。所以采用标准的「环节去重用户」口径并在指标字典里披露。分平台看：京东三段都在 93% 以上、全链路 83.15%；淘宝 88.40%/83.27%/86.50%；抖音 81.67%/**72.98%**/86.42%、全链路仅 51.51%。SQL 里用 LAG() 窗口函数算相邻环节转化率、FIRST_VALUE 算累计转化率。我还补了严格路径口径做敏感性对照（加购须先有浏览、下单须有浏览+加购、支付须前三环节齐全）：628 名「有加购无浏览」用户从漏斗消失，全网全链路降到 24.86%，分平台淘宝 28.40% > 京东 23.72% > 抖音 22.95%——平台效率排名发生变化，但抖音加购→下单仍最低（53.90%，淘宝 62.68%），**「抖音卡在中段」的结论在两种口径下都成立**；严格口径绝对值受日志独立采样影响失真，只做对照不做主口径。还要强调口径边界：漏斗的「下单」来自行为表（事件口径），与订单表的购买用户不是同一件事——全网 1,953 名行为下单用户中只有 640 人（32.77%）在订单表有已完成订单，抖音 670 人中只有 163 人（24.33%），因此漏斗转化率不能用来说明成交结果（报告 1.4 节口径衔接段、`output/metrics/behavior_order_overlap.csv`）。

**Q7：GMV、有效订单量、客单价的口径是什么？订单金额和明细对不上怎么办？**

参考答案：有效订单定义为 `order_status='已完成'`，GMV 是已完成订单 total_amount 之和 = 5,692,092.13 元，有效订单 2,216 笔，客单价 = GMV/订单数 = 2,568.63 元（分母是订单不是用户）。我做了金额勾稽：27,523 行明细全部满足 item_total = quantity × unit_price（0 行超 0.02 元误差），且每笔订单 total_amount 恒等于该单 item_total 之和（10,996/10,996，差额 0）。需要特别注意的是 discount_amount、shipping_fee、tax_amount 是**独立展示字段，没有从 total_amount 里扣减**，所以 GMV 直接用 total_amount，不能再去做减优惠加运费的调整。品类 GMV 用明细 item_total 汇总，与订单 GMV 全额勾稽。

**Q8：讲一下 RFM 的计算和分层规则，打分方向上有什么容易错的点？**

参考答案：只对有已完成订单的 1,643 名用户计算：R = 快照日 2026-12-31 减最近一次有效订单日期，F = 有效订单数，M = 有效消费总额，再各用 `NTILE(4)` 等频打 1~4 分。容易错的是方向：NTILE 按 ORDER BY 顺序把行放进 1~4 桶，**价值越高分要越高**，所以 F、M 要 ASC 排（最高频/最高额落在第 4 桶），R 因为越小越好要 DESC 排（最近消费落第 4 桶），我第一次就写反过 F/M 方向导致分层全部失真。分层规则互斥穷尽：R/F/M 都 ≥3 为高价值；R≤2 且 F 或 M≥3 为流失预警；R≥3 的其他人为潜力；剩余为低价值。结果：高价值 434 人（26.42%）贡献 46.48% GMV，流失预警 380 人（23.13%）贡献 30.01%，潜力 387 人 11.28%，低价值 442 人 12.23%。之所以不用 K-Means，是因为业务要的是可解释、可运营、阈值可审计的分层，不是几何簇。

**Q9：Cohort 留存怎么定义？最近批次留存很低，是不是说明业务更差了？**

参考答案：以注册月份为批次，留存率 = 注册后第 1~N 天内还产生过已完成订单的用户 / 批次注册人数，N 取 30/60/90，用 julianday 日期差实现。不能直接拿最近批次比，因为**观察窗口不完整**：2026-10 批次的 60/90 天窗口在快照日前根本没走完，我在 SQL 里算了 complete_30d/60d/90d 标记，只对窗口完整的 21 个批次取均值，30/60/90 天分别是 1.78%、3.22%、4.66%，结论是复购极弱但不是「越来越差」。另外注册前订单 offset 为负不计入留存，受 50.01% 时序异常影响，绝对值可能低估，我在报告里给了中置信标注，没有夸大结论。为了量化低估幅度，我重跑了一版「注册前订单全部计入」的宽松口径（offset ≤ N）：同样 21 个完整批次均值为 30/60/90 天 15.29%/16.49%/17.70%，比主口径高约 13~14pp，但仍属很低水平——**「复购引擎缺失」的定性结论在两种口径下都不变**，两组数字在报告附录里并列披露。

**Q10：帕累托分析得到头部 20% 用户只贡献 43.4% GMV、头部 20% SKU 贡献 47.63%，怎么解读？**

参考答案：都明显低于经典 80/20。实现上用 `NTILE(5) OVER (ORDER BY M DESC)` 取第 1 组作为头部 20%（329 个用户、409 个动销 SKU）。业务含义有两面：好的一面是没有依赖少数大客户/大单品，结构分散、抗风险强；需要注意的一面是头部经营不足——资源聚焦的边际收益高，把头部 20% 用户贡献从 43% 往 55% 拉，比给所有人发普惠补贴高效。商品侧同理：409 个爆品 SKU（12.40%）已经扛了 47.63% GMV，保供和交叉推荐的确定性收益很高。

**Q11：爆品和滞销 SKU 是怎么定义的？库存状态字段帮上忙了吗？**

参考答案：因为没有库存量、stock_status 又全是「有货」，我用**动销速度**做代理：爆品 = 动销 SKU 中有效销售额前 20%（NTILE(5) 第一桶）且有货，共 409 个；滞销 = 观察窗口内零有效成交，共 1,255 个（38.05%）。滞销又拆成两层：358 个全窗口从未被下单（建议清仓/下架评估），897 个只出现在待付款/取消等非完成订单里（说明「有人拍没成交」，应查价格、详情页、评价、运费）。这个代理口径的局限我明确写进了报告——真实业务必须补库存量和库存金额字段，才能识别真正「高库存积压」的 SKU。另外子品类全是「其他」，也无法做子品类下钻。

**Q12：EDA 有哪些值得说的发现？设备类型对比做了吗？**

参考答案：① 年龄段转化率差异不大（27.82%~31.46%），但 46-60 岁基数最大、贡献 36.95% GMV，26-35 岁客单价最高（2,664.61 元）；② 10 城转化率极差仅 4.44pp（深圳 32.11% 最高、上海 27.67% 最低），地域不是主要分化变量；③ 2000 元以上价格带贡献 57.99% GMV，低价引流款的逻辑在数据里不成立；④ RFM 行为对比里流失预警人群客单最高（3,458 元）却平均 504.5 天没买，召回 ROI 预期最大。设备类型我**没有硬做对比**——device_type 100% 是 mobile，单值维度不可能产生结论，如实写「不具备数据条件」，这比强行分组硬画一张图更重要。我还跑了一个默认参数逻辑回归做特征方向验证：训练集 AUC = 0.78，但基线对照（`output/metrics/lr_baseline.csv`）显示，仅用「收藏 + 加购」两个特征 AUC 就有 0.7702，去掉它们只剩 0.6492，仅人口属性 0.5124、仅平台 0.5429；也就是说判别力来自中段意图信号，年龄/性别/等级几乎不提供信息。而且收藏、加购本就是下单的前置动作（有加购者下单率 57.76% vs 无加购 28.42%），所以这不是「发现」而是量化验证。这个模型只用来交叉印证，没有交叉验证、相对最简基线也没有实质提升，不是可用的预测模型。

**Q13：SQL、Python、Excel 三重校验具体怎么做？为什么要三重？**

参考答案：SQL 是口径源头，`data_process.sql` 共 22 个 SECTION（1 个建视图的 setup + 5 个数据质量复核 + 16 个指标结果分段），其中 11 个 SECTION 使用窗口函数（LAG / FIRST_VALUE / NTILE / ROW_NUMBER / CUME_DIST / SUM() OVER）；Python 用 pandas 不读 SQL 结果独立重算，9 项核心指标逐项比对并落盘 `cross_check_sql_python.csv`，9/9 一致（GMV 5,692,092.13、漏斗 2711/2368/1953/1734）；Excel 腿不是「只写手册」——根目录 `cross_check.xlsx` 用旧版兼容写法（SUMIFS / COUNTIFS / VLOOKUP / SUMPRODUCT + 辅助列）在同一工作簿内重建了同一批指标（订单/明细/行为/商品/用户五张数据表 + 字典表 + 对账表），公式由 Excel 全量重算并缓存，三方结果逐项一致，逐步说明见 `excel_cross_check.md`。三重的价值是防止「同一工具里同样的错误写法自我验证」——比如 shipping_method 重名导致金额翻倍，SQL 按 name 去重、Excel VLOOKUP 只取首个命中、数据透视表用非重复计数，三个独立路径都能暴露问题。

**Q14：如果让你搭 PowerBI 看板，你会怎么设计？**

参考答案：三页。**页面 1 经营总览**：GMV、有效订单、客单价、有效购买用户、RFM 高价值+流失预警 GMV 占比 KPI 卡片，月度 GMV 双轴折线，平台 GMV 环形图，年/月/平台切片器。**页面 2 转化漏斗**：整体漏斗（2711→2368→1953→1734）、三平台环节转化率对比折线、各环节流失人数条形、品类浏览→下单转化率，用来直接定位抖音 72.98% 的卡点。**页面 3 用户与商品运营**：RFM 分层饼图加 GMV 贡献、Cohort 留存热力图、品类销售柱图、滞销 SKU 明细（可筛「从未下单」的 358 个）、爆品 TOP 榜。数据用 output/bi 里 15 张 fct_/dim_ 聚合表，事实表通过 SKU、用户 ID 和维度表建关系。另外可以加一个**可选第 4 页「订单与促销监控」**：订单状态结构、促销完成率、品类共购 lift 矩阵三张图——但要强调这三页扩展数据经卡方检验各分组无显著差异，是字段的结构观察，不能当真实流失率和促销效果用，所以不与主看板跨页联动。

**Q15：这个项目最大的局限是什么？如果接到真实生产数据，你第一步做什么？**

参考答案：五个局限：① 公开数据集，无真实大促和流量波动；② 营销字段只有 5 类粗标记、无预算曝光触达，算不出营销 ROI；③ 地理只到城市；④ 没有消息触达/召回记录，召回策略无法验证效果；⑤ RFM 阈值基于该数据集且存在订单早于注册的时序异常，需要按真实复购周期重校准；此外库存无数量、设备单值。接到真实数据我会先做三件事：一是跑同一套数据质量脚本并补齐营销、库存、触达字段的血缘核查；二是用真实业务的复购周期（比如从下单间隔分布取中位数）重新标定 R 阈值和 Cohort 窗口；三是把本项目推论出的最高优先级动作（抖音加购未下单券、流失预警高 M 用户召回）做成小流量实验，用真实回收数据回填效果，再决定全量推广。
